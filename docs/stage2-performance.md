# 第二階段純效能比較

這份報告比較 PR #1 的 `eb7ec1c` 與獨立純效能提交 `2e6cc2e`，沒有混入後續自適應策略。全部 **17 組前後比較的輸出雜湊完全相同**：包含完整 80 號分數、全排名、Top 3／4／5，以及嚴格逐期回測的每折候選與結算結果。

## 方法與邊界

- Python 3.12、同一主機、每一個量測使用新的獨立程序，依序執行，設定兩條執行緒。使用相同模型工件、資料、隨機種子及模型超參數。CPU 秒數為所有程序執行緒 CPU 時間總和，不等於牆鐘秒數。
- 100／300／1000 期使用附帶的真實台彩資料快照（1276 期）；只有 10000 筆「下一期特徵」測試使用明確標示的合成資料擴充規模，不用於預測成績或正式實戰。
- 推論比較使用同一份第一階段模型工件；每組 50 次呼叫。特徵呼叫次數依規模為 300／100／30／10 次；投票每組 200 次完整十二組融合。表中呈現每組總時間。
- 完整 Walk-forward 保持相同每 100 折重訓、最多 1000 期歷史、相同因果邊界與既有固定策略。新的 prefix／last-seen 快取限制為一個視窗加 128 折，不隨整個資料庫永久增長。
- 共享訓練張量的嘗試沒有確認穩定收益，已撤回，保留原訓練建構流程。因此不宣稱訓練速度改善。CatBoost 推論另明確傳入執行緒上限，避免其預設自行使用更多 CPU。
- 這是一次依序的端對端量測，不是多次重複的信賴區間，也不是速度或記憶體服務保證。首次載入函式庫、排程與配置器會影響小差距。所有未改善及較高記憶體數字均保留。

## 可支持的結論

- 1000 期完整回測：58.680 → 38.738 秒，程序 CPU 81.336 → 62.209 秒，峰值 489.92 → 489.40 MiB；這次觀察約 1.51 倍牆鐘吞吐量。
- 300 期完整回測：30.215 → 15.208 秒、CPU 38.099 → 23.280 秒；但峰值 **467.35 → 471.07 MiB，增加 3.72 MiB**，不能宣稱這個規模更省記憶體。
- 100 期完整回測：10.908 → 12.400 秒、CPU 14.056 → 15.616 秒，這次較慢，不能宣稱所有規模都加速。
- 八模型同工件、1000 期上下文的 50 次推論：0.993 → 0.695 秒，CPU 1.458 → 1.213 秒，峰值 330.70 → 324.64 MiB。
- 四方法、三種星數的 200 次投票：1.541 → 0.169 秒，CPU 1.549 → 0.176 秒。這是投票階段本身的改善，不能當成整個應用的倍數。
- 各模型的原始訓練樣本、標籤、候選選擇與結算結果保持一致；效能比較沒有提供準確度改善證據。
- 沒有引入 Numba。80 號的矩陣操作、既有 NumPy／SciPy 與可重用前綴已提供收益，尚無實測證明加入 JIT 依賴能抵銷編譯、封裝與維護成本。

## 重現與證據

```bash
git worktree add --detach work/stage1-baseline eb7ec1c
git worktree add --detach work/stage2-final-perf 2e6cc2e
cd work/stage2-final-perf
python scripts/benchmark_bingo.py --baseline ../stage1-baseline --output ../stage2/final-performance --threads 2
```

精確參數、Python／套件版本、CPU 配額及原始分數雜湊位於 `validation/stage2/performance/`。六份 gzip JSON 報告保留 100／300／1000 期完整前後逐折回測。
效能一致性測試位於 `tests/test_bingo_vectorization.py`，涵蓋因果 prefix、5／10／17／20／30／50／60／100／200／300／500／1000 視窗邊界、從視窗外掉出的最後出現號碼、排名平手規則，以及同一八模型工件的完整分數。
